# Экспериментальная координация CRM: capability и границы

Текущий `experimental_process_quiescence.py` — локальный эксперимент, не подключённый к production. `backup_ready` всегда `false`, `restoration_unproven` всегда `true`; пустой `last_recovery_errors` означает только отсутствие ошибки в последовательных локальных проверках. Тест `test_another_owner_can_race_after_sequential_free_readback` воспроизводит закрытие API другим владельцем между его readback и открытием MCP. Повторное чтение само по себе лишь переносит окно гонки.

## Вариант для отдельной разработки

1. До создания CRM runtime сформировать ровно один экспериментальный `LifecycleAuthority` и capability для одного координатора. Он связывается **по идентичности экземпляров**, а не по именам, с API admission, MCP call admission, MCP executor admission и конкретным `AgentControlService`. Повторное связывание, отсутствие хотя бы одной стороны, подмена экземпляра или несовпадение authority — отказ до изменения приёма. Публичные свойства должны быть read-only; приватные поля Python не являются защитой от произвольного кода в том же процессе.
2. При opt-in все поддерживаемые пути изменения ownership этих четырёх барьеров должны требовать capability authority. Старые прямые `begin`/`resume` без неё при opt-in обязаны отказывать; без opt-in прежнее поведение production не меняется. Нельзя считать протокол доказанным, пока реестром вызовов и тестами не установлено, что ни одна штатная ветка не меняет ownership мимо authority. Это включает `ApiServer.begin_request_drain`/`resume_requests`, MCP `begin_drain`/`resume`, agent `begin_background_pause`/`resume_background`, а также конкурентные `AgentControlService.start_scheduler`, `start_worker` и `close`, которые меняют исходное состояние потоков.
3. Общий lifecycle lock удерживается при атомарном изменении ownership и во время всего обратного переключения: API → executor → agent → MCP calls. Под ним же каждый компонент проверяет capability и свой фактический owner. После каждого снятия требуется readback `free/owned/foreign` под тем же authority; чужой owner, потерянная привязка или неизвестный результат блокируют открытие зависимых входов. Доступные отдельные методы не должны позволять другому координатору закрыть API сразу после его readback. Новый отдельный запуск после завершения восстановления также возможен только через тот же арбитр с проверкой зависимостей, иначе гонка просто переносится за конец транзакции.
4. Порядок захвата блокировок фиксируется как authority → локальный mutex компонента. Нельзя захватывать authority, уже удерживая локальный mutex. Никаких внешних callback, сетевых вызовов, ожидания задач или `await` под общим lock; механизм не должен полагаться на reentrant callback или сигнал, способный с capability повторно изменить другой fence. Отдельно разобрать `AgentControlService.close()`: его ожидание `join` нельзя просто переместить под общий lock, не доказав отсутствие deadlock и сохранение исходного состояния при timeout/SIGINT. Нужны ограниченные и проверяемые переходы, а не освобождение старого writer по предположению.
5. Координатор создаёт уникальные owner до begin и отдельно записывает подтверждённый атомарный отказ из-за чужого owner. Неизвестный begin, потеря ownership, непонятный readback или неизвестный resume не повторяют автоматически и не открывают зависимые входы. SIGINT между фиксацией результата и выходом, завершение процесса, Docker restart и reboot требуют отдельного долговечного журнала и внешнего recovery: процессный lock/capability после смерти процесса это не решает. Пропущенный scheduler tick сохраняет прежнюю политику catch-up; очередь и возможные неизвестные эффекты требуют отдельного reconciliation, а не переигрывания.

## Проверки до возможного использования

- На искусственных данных проверить отказ прямого begin/resume без capability, единственность связки, все прежние публичные входы и попытку подменить любой компонент. Одновременно другой поток должен попытаться закрыть API между readback и открытием MCP: до конца транзакции он не должен изменить owner; после неё нельзя разрешать частичную смену зависимых fence в обход арбитра.
- Проверить lock ordering, конкурентные start/close agent, активный API handler и MCP worker, отмену, SIGINT на каждом переходе, timeout и неизменность ранее выключенных потоков. Отдельно проверить отсутствие deadlock и что незавершённый или неизвестный effect не повторяется. Повторять сигналы и вызовы без восстановления исходного состояния недопустимо.
- Это только локальные барьеры. До снятия `restoration_unproven` и тем более до резервирования нужны доказательства по OAuth routes/lookup, detached work и сети, host/deploy writers, очередям и Manager ledger, точной версии/составу CRM, WAL, Docker watchdog/restart и восстановлению при потере процесса. Требуются отдельные инструкции и один изолированный restore. До этого никакой результат этих тестов не устанавливает `backup_ready=true`.
