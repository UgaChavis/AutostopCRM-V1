# Граница Store54 при выпуске только Manager и CRM

Статус: source-only разбор и требования будущего окна. Рабочие процессы, БД, credentials, Docker и сеть сервера не проверялись и не изменялись. Этот документ не подтверждает выполненный drain или готовность к обновлению.

Сценарий: будущий `FINAL_MANAGER_SHA` (узкое исправление PR130 поверх `5bf9570cb2029deda70b80a775d6c534d0dca56d`) и `FINAL_CRM_SHA`; Store остаётся на `54eecff7243576a18a47759085323794783d1f9e`, с прежним image/DB/schema/volumes и независимо работающим public-приложением. Store restart/update/migration не входит в обычный путь. Snapshot CRM для приведённых строк: `877b7e160317eb54c51e984ca18d61c5d16a1648`; это не окончательный опубликованный SHA.

Отложенный расширенный Store update сохранён отдельным локальным коммитом `ccea9b38f64c39e5fbd7c227b225f1435983c902` и в `reports/manager/cold-store-wip-ccea9b3/`. Его source3/inputs2/profile5 и новые Store templates не являются обязательными входами этого сценария и исключены из whitelist выпуска.

## Обязательные условия без обновления Store

1. **Разделить области владения.** Profile `crm_manager_all_profiles_cold_v4`, source-package.v2 и producer-inputs.v1 восстанавливают заявленную CRM/Manager область. Нельзя приписывать им Store quiet, отсутствие Store handlers, полную Store backup/offhost restore, immutable Store admission gate или миграцию0069. `old_writer_allowed=false` относится к retired Manager/CRM actors; независимо работающий Store54 не объявляется запрещённым старым writer. Store public/background данные нельзя перезаписать историческим backup Manager/CRM.
2. **Сохранить NoREPEAT вместо невыданного Store quiet claim.** Старые Manager roles и старый CRM retired/denied по cold-контракту. Все source-defined старые action IDs/receipts остаются в tombstones/Store ledger; unknown исходы — только manual reconciliation без resend. Уже принятый Store request может выполнить ПЕРВЫЙ effect позднее; новые Store данные сохраняются. Отсутствие Store inflight=0 само по себе не блокирует этот сценарий, потому что Store не останавливается, не восстанавливается и его quiet не обещается.
3. **Проверить credentials и права.** Отдельно принятые новые credentials привязаны к прежним principal_id с нужными scopes; old keys независимо получают401/403 на применимых Agent/owner транспортах. Сохраняются тот же principal_id и тот же operation/idempotency key для любого reconciliation; не создавать новый ID ради повтора. READ/QUOTE/MANAGE/OWNER scopes и exact endpoint проверяются на искусственном стенде и затем fresh readonly readback. Secret bytes в kit не хранятся. Credential row/configuration change — отдельная разрешённая операция будущего окна, не Store image/schema update. Revocation не выдаётся за отмену уже принятого handler.
4. **Fresh boundary относится к Manager/CRM.** Нужны подтверждённые original retirement/hold, полный source-defined ID catalog, unchanged tombstone bindings и новые пустые queues. При неизвестном Manager/CRM writer, неполном catalog, смене principal/operation namespace, автоимпорте старой очереди, потере запрета retry или неправильном Store auth — STOP до OPEN. Нельзя выдавать manual unknown как not_applied либо повторно запускать old job.
5. **Store stop — только отдельное исключение.** Если позже потребуется обещать Store quiet/backup/update или остановить его по доказанной причине, это другой отдельно допущенный шаг. Потребуются container/image/DB/env/volumes/watchdog/old transport ownership, реальный drain/stop и сохранение всех новых данных; unknown означает STOP. Обычный Deploy VPS/rollback trap не выполняется как часть Manager/CRM release. В текущем основном сценарии Store restart не нужен.
6. **Не объявлять готовность по source-only сверке.** Targeted compatibility run на Store54 и final Manager/CRM tuple обязателен. Если фактические policy/scopes/history несовместимы, остановиться и отдельно обосновать необходимое узкое изменение; не переносить весь RC/WIP автоматически.

## Нужен ли дополнительный base code

Для этой ограниченной гарантии NoREPEAT не обнаружена необходимость нового Store app gate, Store stop, source3/profile5 или миграции. Отдельно найден необходимый **Manager decoder fix**: база5bf отвергает существующие Store54 `payment_status`/`paid_at` в `mark_order_ready`. Candidate PR130 `af28a4e39da6a184072c75d75f6858cfcc34f61c` принимает только эти штатные поля и строго проверяет типы; final merge/source sealing пока ожидаются. Late first execution Store54 не является повтором нового Manager и не противоречит Manager/CRM-scoped old_writer_allowed=false. Исходные Store DB/receipts не переносятся и не восстанавливаются, поэтому их поздние записи не теряются.

В source54 нет общего admission lock или независимого счётчика уже авторизованных Agent/owner handlers; **поэтому не обещаем Store quiet/no-handlers**, а не вводим новый блокер. Если позднее понадобится именно это более сильное свойство, потребуются отдельный independently measured drain/stop либо минимальный дополнительный seam. Сейчас это не часть Manager/CRM profile4 release. Все перечисленные реальные runtime/readback/credential/namespace подтверждения остаются свежими условиями будущего окна; никакие текущие process/DB/auth proofs здесь не получались.

Проверка compatibility fix на искусственных данных: реальный Store54 API → SDK candidateaf28, сохранённый CLAIMED receipt после ротации credential на том же principal, SDK POST1, notifier0, old401/new200; JUnit `reports/manager/store54-action-projection/store54-actual-bridge.xml`, SHA256 `e4d273e0877616d7250b2f7745d7b437cf3c5fa43ba3640f9cc89a05c04e7794`. Это fixture compatibility evidence, не измерение установленной БД или гарантия готовности окна.
